Namaa — ADMIN-SIDE REACT APPLICATION DOCUMENTATION
=============================================================

Welcome to the official technical documentation for the admin-side React application of the Namaa graduation project. This document serves as a complete reference for frontend developers, platform administrators, and support teams, detailing the application's architecture, workflows, access controls, page-level details, and API integrations in a format that can be copied directly into Microsoft Word.

________________________________________________________________________________


1. Project Overview
-------------------

Namaa is a premium, AI-driven business analytics platform designed specifically for Small and Medium Businesses (SMBs). While the client-side application allows SMBs to query their databases and view analytics, the Admin Dashboard serves as the central control plane of the platform.

1.1 Core Audiences:
• Platform Administrators: Superusers with full privileges to manage the platform, assign roles, edit database configurations, and control internal team membership.
• Superusers: Core operations personnel who manage active plans, verify database connectors, configure services and packaging details, and coordinate pricing.
• Support Agents: Customer service representatives who audit system logs, resolve client lockout issues, inspect billing invoices, and troubleshoot database connections.

1.2 Key Capabilities:
• Role-Based Access Control (RBAC): Centralized management of platform roles and granular inheritable permissions.
• Client Profile Inspector: In-depth verification of customer companies, including subscription details, active database connections, and custom Tableau dashboards.
• Service & Packages Builder: Tools to manage modular services, adjust pricing levels, configure discount periods, and set token allocations.
• Revenue and Subscription Controls: Centralized logs of orders, invoices, and active customer subscriptions with advanced server-side sorting, price filtering, and expiry warning highlights.

3. Component Architecture
-------------------------

This section documents the non-page, structural UI components used as global layouts, navigation panels, route guards, or reusable cards.

3.1 Route Guards

3.1.1 Protected (Protected.jsx)
• Category: Security Route Guard.
• Purpose: Restricts access to dashboard workspaces for unauthenticated sessions.
• Properties: Accept "children" (React Node) to render upon successful validation.
• Behavior: Reads "userToken" and "loading" states from "userContext". If loading is true, displays a placeholder spinner; if authenticated, renders children; if unauthorized, redirects the session to the public login root ("/").
• Dependencies: react-router-dom, userContext.

3.2 Layout Components

3.2.1 Layout (Layout.jsx)
• Category: Layout Container.
• Purpose: Serves as the primary admin workspace shell containing sidebar navigation and headers.
• Behavior: 
  - Left-hand Sidebar: Contains navigation links for all admin modules. Supports mobile slide-out controls (via "isMobileOpen") and desktop collapsing (via "isCollapsed" state).
  - Header: Displays dynamic breadcrumbs computed on route changes, fetches administrator details on mount via "GET /Accounts", and handles session logouts by clearing tokens and redirecting to the login root.
• Dependencies: react-router-dom, userContext, api.

4. Page-by-Page Walkthroughs & Operational Flows
------------------------------------------------

This section details every page component, mapping its purpose, layout design, internal states, behavioral logic, data inputs, and user journey steps.

4.1 Admin Home & KPI Dashboard (Admin.jsx)
• Mapped Route: /dashboard
• Purpose: Serves as the primary landing dashboard for logged-in administrators. It provides a high-level operational overview of active users, security roles, and user account status distributions across the system.
• What is Displayed:
  - KPI Stat Cards: Five prominent numeric widgets aligned at the top showing Total Users, Active Users, Inactive Users, Disabled Users, and the number of configured security roles.
  - User Status Chart: A Recharts Pie Chart visualizing the percentage breakdown of active vs. inactive or locked administrative accounts.
  - Role Distribution Chart: A Recharts Treemap Chart showing a hierarchical breakdown of user counts per security role. Active roles are colored green, and disabled roles are highlighted in red.
• User Interactions & Controls:
  - Hovering over chart elements triggers interactive tooltips displaying absolute counts and percentages.
  - Clicking on individual segments within the charts filters metrics or links directly to filtered sections.
  - The side-navigation panel remains fully responsive, updating sizing automatically on different screens.

4.2 Custom Roles Builder (Roles.jsx)
• Mapped Route: /dashboard/roles
• Purpose: Governs role creation and security permissions management. It enables administrators to create new operational roles and assign granular system privileges.
• What is Displayed:
  - Left-hand Grid: A directory list of existing roles displaying the role name, description, active member counts, and a status toggle switch.
  - Right-hand Form: A role creation card with text inputs for the role name and description, followed by a grid of permissions check boxes.
• User Interactions & Controls:
  - Permissions Checklist: Features toggles for permission assignment ("Add") and permission inheritance ("Inheritable"). Deselecting the "Add" toggle automatically resets the "Inheritable" flag to false.
  - Status Toggle: Allows disabling or enabling an existing role. Clicking this toggle prompts a SweetAlert2 confirmation dialog to prevent accidental changes.
  - Submit Actions: Submitting the form validates inputs using Formik/Yup and makes a request to create the role, automatically updating the left-hand directory list upon success.

4.3 Role Inspector (RolesDetails.jsx)
• Mapped Route: /dashboard/roles/:id
• Purpose: Displays a detailed audit view of a specific security role, its assigned permission matrix, and its audit logs.
• What is Displayed:
  - Title Section: Displays the role's name, active member count, and status badge.
  - Relations Panel: Shows interactive buttons indicating who created, updated, or currently manages the role.
  - Permissions Matrix Table: A read-only table displaying the full permission names, active flags, and inheritance settings.
• User Interactions & Controls:
  - Clicking on the creator or updater buttons redirects the administrator directly to the profile view of the corresponding team member.
  - The back button returns the user to the main roles directory.

4.4 Internal Team Directory (Users.jsx)
• Mapped Route: /dashboard/users
• Purpose: Manages the directory of administrative team members, support agents, and system superusers.
• What is Displayed:
  - Add User Button: Opens a popup modal containing form inputs for first name, last name, email, password, and role selection.
  - Filter Toolbar: A search input box for search queries, coupled with dropdown selectors to filter by role, active status, or account lock status.
  - Team Directory Table: Displays member names, email addresses, assigned roles, creation timestamps, and active status switches.
• User Interactions & Controls:
  - Search Input: Supports searching across multiple properties. Enter query keywords (e.g. name or email) to filter the table.
  - Sorting: Clicking table column headers toggles the sort order (ascending/descending) for columns like registration date.
  - Modal Form: Formik validates input fields (e.g., email format and password strength) and submits the new user record on completion.

4.5 System User Details (UserDetails.jsx)
• Mapped Route: /dashboard/users/:id
• Purpose: Provides an inspection page for a specific administrative user, detailing security logs and account settings.
• What is Displayed:
  - Contact Profile: Displays the user's name, email address, role, and avatar.
  - Statistics Panel: Shows the total number of login attempts, failed login counts, and the last active session timestamp.
  - Action Controls: Buttons to toggle status (Active, Inactive, Blocked) or trigger password resets.
• User Interactions & Controls:
  - Toggling account status triggers a SweetAlert2 confirmation box. Confirming updates the account status on the backend.

4.6 User Privilege Audit (MyPermissions.jsx)
• Mapped Route: /dashboard/my-permissions
• Purpose: A self-service audit page allowing the currently logged-in administrator or support agent to view their own active permissions.
• What is Displayed:
  - A clean, read-only list displaying all permissions assigned to the active user's role.
  - Status indicators showing whether each permission is active or inheritable.
• User Interactions & Controls:
  - Includes a quick search bar to filter permissions by keyword.

4.7 Clients List (Clients.jsx)
• Mapped Route: /dashboard/clients
• Purpose: Manages registered customer business accounts using the Namaa platform.
• What is Displayed:
  - KPI Summary Panel: Displays four metrics cards showing Total Clients, Active Clients, Locked Accounts, and Inactive Clients.
  - Advanced Filter Bar: Contains search inputs for company names, positions, or emails, along with account lockout filter dropdowns.
  - Clients Directory Table: Details business names, positions, registration dates, database connection counts, and account status toggles.
• User Interactions & Controls:
  - Lockout Recovery: If a customer account is locked due to too many failed login attempts, an "Unlock" action button is displayed.
  - Status Toggles: Clicking the status toggle switch prompts a SweetAlert2 confirmation dialog to disable or enable the client's access.

4.8 Customer Profile Inspector (CustomersView.jsx)
• Mapped Route: /dashboard/customersview/:id
• Purpose: Centralizes all information related to a single customer business, including linked databases and active subscription plans.
• What is Displayed:
  - Business Metadata Card: Shows contact names, positions, companies, registration dates, and active Tableau URLs.
  - Activity Metrics: Summary widgets for total orders placed, reviews submitted, and database connections established.
  - Database Connections Grid: Lists database engines (PostgreSQL, SQL Server, etc.), connection names, database hosts, and connection health check badges.
  - Subscription History Table: Shows details of active and expired plans.
• User Interactions & Controls:
  - Add Tableau URL Button: Launches a modal to set a custom Tableau dashboard URL for the client. Formik validates the input URL before submission.
  - Database Health Audit: Supports triggering manual connection test runs from the connected database list.

4.9 Services Management (Services.jsx)
• Mapped Route: /dashboard/services

• What is Displayed:

  - Toggle Switch: Clicking a status switch sends an update to enable or disable the service, updating the card's visual state.

4.10 Service Builder & Modifier (AddServices.jsx & EditServices.jsx)

4.12 Package Builder & Modifier (AddPackages.jsx & EditPackages.jsx)
• Mapped Routes: /dashboard/packages/add & /dashboard/packages/:id/edit

  - General Package Form: Fields for package name, description, duration, base price, level, and priority.

  - Service Config Panel: Renders input cards for every selected service to set token allocations.

4.13 Orders Directory (Orders.jsx)

• What is Displayed:

  - Filter Inputs: Adjusting price sliders or date pickers automatically filters the table.

5. Authentication & Security Flows
----------------------------------

Authentication is managed via JSON Web Tokens (JWT) stored in browser storage, with token updates handled automatically during active sessions.

5.1 Axios Interceptors and Silent Token Refresh
The Axios configuration in src/api.js manages authorization headers and automatic token updates:
• Request Interceptor: Automatically injects Authorization: Bearer <token> into outgoing headers if a token exists in localStorage.
• Response Interceptor & Silent Refresh:
  - Detects 401 Unauthorized responses.
  - If a refresh process is not already running, it flags isRefreshing = true and calls POST /Auth/refresh, passing the stored refresh token.
  - While the refresh request is active, other failing requests are added to a failedQueue array.
  - Success Handler: Resolves the failedQueue with the new token, replays the requests, and updates localStorage.
  - Failure Handler: Clears the queue, removes tokens from localStorage, resets contexts, and redirects the user to the login screen ("/").

6. API Integration Architecture
------------------------------

The Admin Dashboard communicates with the backend REST API using a centralized HTTP client architecture designed for secure session management and structured data processing.

6.1 Centralized HTTP Client (api.js)
API communications are managed by a centralized Axios client instance configured in src/api.js. This client sets a relative base URL ("/api") to integrate with proxy redirect rules (configured via netlify.toml and vercel.json) and sets "withCredentials: true" to ensure cookies are sent with requests.

6.2 JWT Authorization Interceptors
The client incorporates request and response interceptors to handle authentication:
• Outgoing requests automatically inject the JWT token from localStorage into the "Authorization: Bearer" header.
• Incoming responses check for "401 Unauthorized" errors. If a session expires, a silent token refresh process is initiated:
  - The failing request is paused, and subsequent requests are queued in a request queue.
  - A single request is sent to the "/Auth/refresh" endpoint to exchange the expired token for a new access token.
  - If the refresh request succeeds, the new token is saved, the queued requests are updated with the new token, and the failed requests are retried.
  - If the refresh request fails or no refresh token is available, the session is cleared, localStorage is reset, and the user is redirected to the login screen.

6.3 Data Query and Filtering Architecture
Most list views use a POST query pattern (such as "/users/search" or "/Clients/search") rather than GET queries:
• Search requests send a structured JSON payload containing search keywords, pagination parameters (PageNumber, PageSize), sorting parameters (SortColumn, SortDirection), and active filter values.
• This payload-based filtering model keeps the request URL clean and supports complex search queries.

6.4 Multipart Form Submissions
Forms that handle file uploads (e.g. creating services in AddServices.jsx or updating icons in EditServices.jsx) submit data as multipart form-data:
• Formik handles form state tracking, and submitting the form packages text inputs and binary files into a FormData object.
• The Axios client automatically sets the appropriate headers for multipart submissions.

6.5 User Feedback and Confirmation Guards
The application provides visual feedback and confirmation guards during API interactions:
• Non-blocking toast notifications (React Hot Toast) display real-time status updates (e.g., "Updating package...") and success or error states.
• Destructive API actions (e.g. locking customer accounts, toggling security roles, or terminating active subscriptions) are protected by confirmation dialogs (SweetAlert2) to prevent accidental changes.

7. Performance Optimization, Known Issues & Future Improvements
----------------------------------------------------------------

7.1 Performance Optimization
• Debounced Form Inputs: Search input fields on the internal users page feature debounced updates to limit API search requests during typing.
• Optimistic UI: Subscription renewal toggles update the local state immediately, reverting only if the backend request fails.

7.2 Known Issues
• Tableau URL Persistence: Tableau URLs must be set for each active subscription; changing a subscription resets the Tableau URL configuration until configured again.
• Marquee Loop Render: Under heavy system loads, the analytics Treemap rendering may lag slightly on browsers without full hardware acceleration enabled.

7.3 Future Improvements
• TanStack Query: Integrate React Query to cache roles and service compositions locally, reducing redundant network requests.
• WebSocket Event Logs: Utilize WebSockets (SignalR) to push subscription lifecycle events and logs to the Subscription View console in real time.
